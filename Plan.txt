Codex Master Implementation Plan

Project Context

Primary writable repository:

TravPlanner

Secondary read-only reference repository:

TravelPlanner

Working branch:

codex/combine

The primary repository contains the existing Next.js frontend.

The secondary repository contains the authoritative Firebase backend architecture, shared schemas/contracts, Firestore model, callable functions, validation logic, security rules, and tests.

The objective is to turn TravPlanner into the integrated application.

The backend integration is already substantially complete. The remaining work focuses on:

restoring the original frontend experience;
replacing manual Google Place ID entry with proper Places Autocomplete;
preparing the repository for production deployment;
validating the deployed application.

Frontend Preservation Rule

The frontend branch is the visual source of truth.

Preserve where technically possible:

page structure
component hierarchy

Replace only:

Do not replace an existing designed component with plain inline markup when that component can be adapted to real backend data.

Primary rule:

Remove fake data and incompatible business logic, not the frontend design.

Do not redesign a page purely because a simpler implementation is easier.

Required Frontend Comparison Procedure

Before restoring or modifying an important page/component:

Open the corresponding implementation from branch frontend.
Open the current implementation from branch codex/combine.
Compare page structure, components, interaction patterns, and styling.
Identify UI elements lost during integration.
Restore the original visual structure using the new Firebase hooks, repositories, callable APIs, and shared types.
Do not restore mock/localStorage authoritative state.
Verify that the resulting page is visually and structurally closer to frontend than the current simplified combined implementation.

Important backend incompatibilities should be documented rather than hidden.

Phase 40 — Google Places Autocomplete

Objective

Replace manual Google Place ID, latitude, and longitude inputs with normal user-facing Google Places selection.

This is a P0 requirement before production deployment.

Create

└── PlaceAutocomplete.tsx

Supporting files may be added under:

lib/maps/
lib/places/

if useful.

Use On

app/trips/new/page.tsx
app/trips/[tripId]/places/page.tsx

Component Output

Return normalized browser selection data:

{
  placeId: string;
  name: string;
  lat: number;
  lng: number;
}

Optional presentation-only fields may include:

formattedAddress?: string;

Create Trip Behavior

User should type:

Tokyo

and select:

Tokyo, Japan

The form should automatically populate internal:

placeId
name
lat
lng

Do not require users to manually know or enter these values.

Candidate Submission Behavior

User should search for:

Tokyo Skytree

and select a real provider place.

Do not expose raw Place IDs as the normal interface.

Environment

Use:

NEXT_PUBLIC_GOOGLE_MAPS_BROWSER_KEY

for browser-side Google Places integration.

This browser key is separate from the backend secret:

GOOGLE_MAPS_API_KEY

Authority

Browser-selected data is used for UX and request construction.

The backend remains authoritative and must continue resolving/validating provider Place IDs.

Do not trust browser-provided place information as final backend truth.

API Key Restrictions

Document that the browser key should be restricted using appropriate HTTP referrer and API restrictions.

Do not reuse the server Functions secret as a browser key.

Development Fallback

Manual Place ID input may exist only as an optional development/debug fallback.

It must not be the normal production UX.

Phase 42 — Production Deployment Checklist

Objective

Deploy the application when the required Firebase, Google Cloud, and Vercel access/configuration is available.

This phase may require manual operator actions and external credentials.

Do not fabricate successful deployment.

Step 1 — Firebase Project

Create or select a Firebase project.

Ensure the project supports Cloud Functions deployment.

Use the Blaze billing plan if required by Firebase Functions deployment.

Configure billing/budget alerts.

Step 2 — Firebase Authentication

Firebase Console:

Authentication
→ Sign-in method
→ Google
→ Enable

Ensure Google authentication is correctly configured.

Step 3 — Google APIs

Enable the APIs required by the backend and browser integration.

At minimum inspect actual backend/browser code and enable the required equivalents for:

Google Places
Google Routes
Maps/Places browser integration

Do not enable unnecessary APIs.

Step 4 — Browser Google Key

Create a browser key for:

NEXT_PUBLIC_GOOGLE_MAPS_BROWSER_KEY

Apply appropriate restrictions.

Recommended:

HTTP referrer restrictions
API restrictions

Use production and preview domains as appropriate.

Step 5 — Backend Google Secret

Set:

firebase functions:secrets:set GOOGLE_MAPS_API_KEY

Use a server-side Google API key with suitable API restrictions.

Do not use the browser key.

Step 6 — Deploy Firestore

Deploy:

firebase deploy --only firestore

This should deploy:

firebase/firestore.rules
firebase/firestore.indexes.json

Verify deployment against the intended project before proceeding.

Step 7 — Deploy Cloud Functions

Run:

firebase deploy --only functions

Verify:

build succeeds

Step 8 — App Check

Never use App Check debug tokens in production.

Decision Rules for Ambiguity

When frontend behavior conflicts with backend behavior:

Use backend behavior.

When backend docs conflict with actual exported code:

Use actual exported code.

When a frontend visual feature can be retained without violating backend contracts:

Retain it.

When a frontend component uses mock data but its UI remains useful:

Adapt the component rather than deleting it.

When a feature exists only in frontend mocks and has no backend equivalent:

Hide or downgrade the feature.

When a backend field is optional:

Do not invent data unless there is a clearly safe UI default.

When required backend information is missing from the frontend:

Add the smallest UI necessary to collect it.

When there is no suitable UI for a secondary backend feature:

Do not redesign the application around it. Prioritize the primary workflow.
